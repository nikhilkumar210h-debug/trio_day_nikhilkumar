━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. PRODUCT IDENTITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Product Name: Trio Day

Browser title: Trio Day — Do Something Worth Coming Back To

Core tagline: The place you open when you want to do something meaningful.

Trio Day should feel like a serious, premium, modern technology product — not a school project or generic social-media clone.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. THE CORE IDEA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Trio Day is NOT primarily a social-media application.

Its purpose is to give people things they can actually do:

  solve / learn / build / create / practice / compete / collaborate / participate / help / improve

The fundamental product question:

  Instagram: "What do you want to see?"
  Trio Day:  "What do you want to do?"

Social features exist only to make meaningful activities better.

Posts, comments, stories, chat, reactions, profiles — these support the activity ecosystem, they are NOT the product itself.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. THE MAIN MOTIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Trio Day should become:
  The place you open when you want to do something meaningful.

Master product rule:
  Build Trio Day as a premium, fast, privacy-conscious, free-tier-friendly action platform
  where personalization helps users discover meaningful things to do,
  community helps them do those things together,
  and social features support — not replace — the core experience.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. WHY TRIO DAY SHOULD BE DIFFERENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Many social apps optimize for:
  Open → Scroll → See content → Scroll more → Repeat

Trio Day optimizes for:
  Open → Discover something meaningful → Start → Do → Complete → Earn progress → Improve → Come back

The user should leave Trio Day feeling: "I actually did something."
Not: "I spent 40 minutes scrolling."

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. RETENTION PHILOSOPHY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Useful retention principles (pointing toward action, not consumption):
  personalization / social presence / progress / streaks / anticipation /
  notifications / community / identity / achievement / FOMO used carefully /
  fast feedback / low friction

BAD notification: "12 new posts. Scroll now."
GOOD notification: "8 people are solving this challenge right now."
GOOD notification: "Your friend completed today's challenge."
GOOD notification: "You're one session away from extending your streak."

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Frontend: HTML / CSS / JavaScript / PWA
Data/backend: Firebase / Firestore / Firebase Authentication / Cloudinary / Cloudflare Workers

Existing functionality:
  posts / stories / voice / comments / reactions / sharing /
  private chat / group chat / notifications / PWA / Cloudinary media /
  community tasks / task templates / XP / streaks / badges /
  leaderboards / recommendations / activity concepts /
  moderation / admin functionality

  users / posts / communityTasks / taskTemplates / leaderboards / privateChats / ...

7. IMPORTANT: DO NOT DESTROY THE EXISTING APP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The existing application has real users, data, functionality and working integrations.

NEVER:
  - blindly rewrite everything
  - delete Firestore collections
  - migrate databases without approval
  - remove Firebase Auth without approval
  - remove Cloudinary without approval
  - assume an existing feature is unused without checking
  - replace working architecture just because a different architecture looks cleaner

INSTEAD:
  Audit → Understand dependencies → Plan → Change incrementally → Test → Review → Commit

However: existing functionality is NOT automatically sacred.
If something is genuinely bad, confusing, low-value or harmful, it can be:
  removed / merged / hidden / replaced / simplified
But the reason and impact must be documented.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
8. TODAY / HOME
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Today should NOT be an endless feed.
Primary question: "What should I do now?"

Possible structure:
  Good evening 👋
  🔥 14 day streak

  TODAY'S FOCUS
  Logic Challenge — 15 min
  [Start]

  Continue
  3 recommended activities
  Live Now
  Your Progress

The most important recommendation should be visually obvious.
Do NOT create a giant dashboard with 20 cards.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. DISCOVER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Discover means: Find something worth doing.

Possible sections:
  For You / Live Now / Challenges / Rooms / People

Posts can exist but should not dominate Discover.

Social signal example: "8 people are doing this right now."
This creates social presence without turning the page into a feed.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
10. DO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Main action categories:
  Solve / Learn / Build / Create / Challenge / Group

Avoid showing dozens of categories.
The UI should make choosing an activity feel easy.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
11. PERSONALIZATION ENGINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Start with a lightweight rule-based recommendation engine, not expensive AI.

Score =
  interest match + difficulty match + time match + previous completion +
  recent behavior + freshness + community activity + quality + creator reputation
  - skip signals - hide signals - report signals

Behavior weights:
  view=weak / open=stronger / start=stronger / complete=strong /
  repeat=very strong / skip=negative / hide=strongly negative / report=strongly negative

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
12. USER-CREATED ACTIVITIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Users should eventually create:
  puzzles / challenges / quizzes / coding tasks / projects / group challenges

User-generated content must NOT become spam.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
13. QUALITY / ANTI-SPAM ALGORITHM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Quality signals:
  completion rate / positive feedback / repeat participation / skip rate /
  hide rate / report rate / freshness / category correctness /
  difficulty correctness / expected-time accuracy / creator history / creator reputation

Safety signals:
  automated moderation / duplicate detection / near-duplicate detection /
  suspicious activity detection / mass creation limits / rate limiting /
  manipulation detection / fake completion detection

Bad activity → lower visibility, lower recommendations, possibly hidden/moderation queue
Good activity → higher visibility, higher recommendation score, better discovery

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Community should answer: "What meaningful things are people doing?"
NOT: "Who is popular?"

Community should emphasize:
  active challenges / people learning / people building /
  group activities / useful creators / live participation / collaboration

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  topic / members / text chat / progress / timer / goal / completion

Video/audio can be added later if product proves it needs them.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Trio Day should feel: Premium productivity + playful intelligence

NOT: generic SaaS dashboard / childish gamification / Instagram clone / giant-card dashboard

AVOID:
  huge empty cards / giant sidebar / excessive borders / card-inside-card /
  huge buttons / three-column clutter / too many navigation items / unnecessary animations

Premium means: clarity + consistency + speed + restraint

Main content max-width: ~720–820px — centered, sides breathe, feels premium not stretched.

24. PRIVACY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Maintain a clear Privacy Policy. Review whenever data flow changes.

Ask: What data collected? Why? Where stored? Who can access? Is it public/private? Necessary? Third party?

Possible public routes: /challenge/... / /puzzle/... / /learn/...
Private user data must never become SEO-indexable accidentally.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  authentication / authorization / least privilege / input validation /
  rate limiting / server-side validation / secure API endpoints /
  Firestore security rules / Cloudinary access controls /

NEVER trust client for: XP / level / completion / admin permission / moderation / private data access

26. CURRENT BACKEND TRANSITION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Target: Flask / Python on Google Cloud Run

Migration must be gradual. Do NOT immediately replace everything.

Pattern:
  Existing Worker functionality → Implement Flask equivalent → Test → Move traffic → Verify → Remove old

27. DATABASE DECISION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Do NOT migrate Firestore → PostgreSQL immediately.
Keep Firestore initially (Flask → Firestore).

Reasons: existing data / existing app / Firebase ecosystem / lower risk / lower complexity
PostgreSQL/Redis can be evaluated later if actual scale demands them.

29. WHY CLOUD RUN + CLOUDFLARE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Frontend-first architecture:
  HTML/CSS/JS → show UI → API calls → populate dynamic data

NOT: HTML → wait for Flask → show UI

Cloudflare serves static assets at edge = fast initial load.
Flask/Cloud Run handles dynamic operations only.

Cold starts are possible but reduced by:
  lightweight Flask startup / minimal dependencies / efficient Firestore queries /
  caching / pagination / batched reads / background/non-blocking UX /
  avoid unnecessary API calls

31. COST CONTROL + FREE TIER RULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Free tier ≠ unlimited traffic. Engineer to reduce unnecessary requests.

⚠️ FIRESTORE COST TRAPS (confirmed with ChatGPT review):

Trap 1 — Realtime listeners:
  onSnapshot() charges reads on every add/update/remove.
  20 users × 5 listeners × many updates = expensive fast.

  RULE: Realtime ONLY where it genuinely improves experience.
  GOOD realtime: Chat / Room progress / Important notifications
  BAD realtime: Every profile stat / Every recommendation / Every leaderboard / Discovery cards

Trap 2 — Flask reads are not free:
  Frontend → Flask → Firestore still generates Firestore operations.
  One page endpoint can quietly perform many reads.
  Every backend feature must have an estimated Firestore read/write cost.

Trap 3 — Security rule evaluation:
  Reads to evaluate Firestore Security Rules can contribute to billed operations.
  Rules must be secure AND efficient.

Trap 4 — Cloud Run billing:
  Cloud Run has free monthly allowances but is usage-based above them.
  Linking a billing account puts Firebase on Blaze plan (still has free quota but billed beyond it).

Cloudinary: resize / compress / responsive formats / avoid large uploads
Cloudflare: cache static assets / long cache headers / compressed assets
Flask: efficient endpoints / avoid startup cost / cache appropriate data

LOW MODEL SAFETY RULES (Nemotron 3 Ultra):

Rule 1 — One phase at a time. Never Phase 2 + 3 + 4 together.

Rule 2 — One logical subsystem at a time.
  For Phase 2: tokens.css → shared CSS → header/nav → sheets/modals →
               chat CSS → theme persistence → accessibility → testing

Rule 3 — Inspect before modifying.
  "Do not edit a file until you have inspected its current implementation and identified dependencies."

Rule 4 — No unrelated refactoring.
  "No unrelated refactoring. If you see old code in an unrelated file, leave it."

Rule 5 — Explicit forbidden actions per phase:
  "Do NOT: change Firestore schema / change authentication / modify master /
   switch branches / merge / delete existing data / add unrelated libraries / start the next phase."

Rule 6 — Require diff review at the end:
  git status / git diff --stat / git diff + completion report

Rule 7 — Commit only at phase boundary.

39. SECURITY TRACK (across all phases)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Security is NOT left until the end. It runs as a track:

  Phase 01: Audit current Firestore rules
  Phase 06-11: Implement features while preserving rules
  Phase 12: Flask security foundation (see below)
  Phase 16: Final security hardening + privacy + SEO

Firestore Security Rules must be tightened BEFORE Flask migration begins.
During migration, both browser→Firestore and browser→Flask→Firestore paths may exist.
Weak rules during that period = unnecessary risk.

Phase 12 Flask security must include:
  Flask authentication verification / Firebase ID-token verification /
  authorization checks / server-side ownership checks / admin authorization /
  input validation / rate limiting / secure CORS / secrets management /
  Firestore service-layer restrictions /
  NO trusting client-supplied XP/completion/admin values
