🟣 TRIO DAY — COMPLETE MASTER PROJECT CONTEXT

This document is the canonical context for the Trio Day project.

Any AI coding agent working on Trio Day must read and follow this document before making architectural, UX, backend, deployment, security, or feature decisions.

1. PRODUCT IDENTITY
Product Name

Trio Day

The product should consistently use:

Trio Day

Browser title can be:

Trio Day — Do Something Worth Coming Back To

Possible core tagline:

The place you open when you want to do something meaningful.

The exact title/meta/canonical/schema should be implemented consistently across the site.

Trio Day should feel like a serious, premium, modern technology product — not a school project or generic social-media clone.

2. THE CORE IDEA

Trio Day is NOT primarily a social-media application.

Its purpose is to give people things they can actually do.

Examples:

solve
learn
build
create
practice
compete
collaborate
participate
help
improve

The fundamental product question is:

Instagram:

“What do you want to see?”

Trio Day:

“What do you want to do?”

Social features exist only to make meaningful activities better.

Posts, comments, stories, chat, reactions, profiles, etc. should support the activity ecosystem rather than becoming the product itself.

3. THE MAIN MOTIVE

The product should become:

The place you open when you want to do something meaningful.

Strong product rule:

Build Trio Day as a premium, fast, privacy-conscious, free-tier-friendly action platform where personalization helps users discover meaningful things to do, community helps them do those things together, and social features support—not replace—the core experience.

11. PERSONALIZATION ENGINE

Trio Day needs personalization because an enormous activity library can overwhelm users.

Start with a lightweight rule-based recommendation engine, not expensive AI.

Conceptual score:

score =
interest match
+ difficulty match
+ time match
+ previous completion
+ recent behavior
+ freshness
+ community activity
+ quality
+ creator reputation
- skip signals
- hide signals
- report signals

Behavior weights:

view       = weak
open       = stronger
start      = stronger
complete   = strong
repeat     = very strong
skip       = negative
hide       = strongly negative
report     = strongly negative

Example:

If someone repeatedly completes Python challenges:

Python recommendation score ↑

If someone repeatedly skips one-hour tasks:

shorter activities ↑

29. WHY CLOUD RUN + CLOUDFLARE

The previous Render idea is not the selected architecture.

Reason:

Free Render-style hosting can sleep after inactivity, causing an unpleasant cold-start experience.

Trio Day wants:

fast, premium UX

Cloudflare handles the static frontend at the edge.

Therefore:

User opens Trio Day
↓
Cloudflare serves HTML/CSS/JS
↓
UI appears quickly
↓
JavaScript requests backend data
↓
Cloud Run Flask API handles dynamic operations

The user should not have to wait for the entire website just because the backend is waking.

30. CLOUD RUN COLD START PROBLEM

Cloud Run can scale down when idle.

Therefore backend cold starts are still possible.

This is a known limitation.

But we reduce the impact by:

Frontend-first architecture

Don't make:

HTML
↓
wait for Flask
↓
show UI

Instead:

HTML/CSS/JS
↓
show UI
↓
API calls
↓
populate dynamic data

Also use:

lightweight Flask startup
minimal dependencies
efficient Firestore queries
caching
pagination
batched reads
background/non-blocking UX where possible
avoid unnecessary API calls

If real-world usage later proves that always-on capacity is necessary, paid capacity can be considered.

Do not sacrifice the product architecture just to avoid a theoretical cold start before measuring actual performance.

31. CLOUD RUN FREE-TIER LIMITATION

Free hosting does not mean unlimited infrastructure.

Cloud Run has a free monthly usage allowance, but it is usage-based and Google can require billing setup.

Therefore:

Free tier
≠
Unlimited traffic

The application must be engineered to reduce unnecessary requests.
